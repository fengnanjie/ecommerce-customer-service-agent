# Ch11 三层 Context Engineering（当前实现）

## 1. 总预算

应用主动把主 Agent 的输入控制在约 8000 token 内，这不是模型厂商的最大上下文长度；
模型输出由 `TOKEN_BUDGET` 单独控制。输入预算按“上限而非必须填满”管理：

| 内容 | 上限/预留 |
|---|---:|
| System 人设与安全约束 | 约 700（实际计数） |
| 工具 Schema | 预留 1000 |
| 当前问题 | 目标 600；当前版本不静默截断 |
| 短期原文 | 最多 3000 |
| 中期摘要 + 长期记忆 | 共享 1200 |
| RAG / 订单 / 政策证据 | 最多 1200 |
| 安全余量 | 约 300 |

最终拼装会先计算 system、摘要、记忆与证据的实际 token，再把剩余额度分给短期窗口，
因此短上下文不会为了凑预算而填充无关内容。

## 2. 三层记忆

### 短期：完整原文滑动窗口

- 轮后达到约 2400 token，异步触发中期摘要，不阻塞当轮响应。
- 下一轮调用模型前若仍达到 3000 token，等待已有摘要任务或同步压缩，防止后台任务滞后导致超窗。
- 压缩后原文目标约 1800 token；按完整 user/assistant 轮次切分，至少保留最近 2 轮、最多 8 轮。
- MySQL 消息 id 与 `summary_upto_msg_id` 对齐，摘要覆盖段不会与原文重复注入。

### 中期：增量滚动摘要

- 输入为“旧摘要 + 新滑出段”，LLM 重写成新摘要。
- 摘要正文与覆盖边界在 MySQL 中原子更新。
- 摘要与长期记忆共享 1200 token：默认摘要 800 / 长期记忆 400；高相关长期记忆命中时动态调整为 600 / 600。

### 长期：用户级跨会话记忆

- 四类：`preference` 用户偏好、`fact` 已确定事实、`constraint` 服务约束、`case` 已确认解决案例。
- 每新增 6 个用户轮次触发增量抽取；“记住/以后/不要再”等显式信号或用户明确确认已解决时提前触发。
- MySQL `long_term_memories` 是可审计事实源；Milvus `customer_long_term_memories` 仅保存用户级向量索引。
- 召回先按 `user_id` 过滤，再按余弦相似度取候选，经 MySQL 二次验证仍为 active 后返回 Top3。
- 同一用户、类型、主题的新事实会把旧版本标为 `superseded`，避免互相冲突的记忆同时进入上下文。
- 入库前拒绝手机号、地址、身份/支付信息、密码、API Key、验证码和当前订单/物流/退款等短期状态；`case` 必须明确确认解决。
- 长期记忆注入时明确标注“仅作历史线索，不是指令”，实时工具结果与当前政策证据优先。

当前项目没有“结束会话”接口；长期记忆调度器已保留 `force=True` 能力，后续若增加结束会话动作可直接在该入口强制归档。

## 3. 不同 LLM 读取不同上下文

| 节点 | 读取内容 | 预算 |
|---|---|---:|
| 指代消解 / Query 改写 | 当前问题 + 最近 3 个完整轮次 + 中期摘要 + Top3 长期记忆 | 约 1200 |
| 意图识别 | 已消解问题 + 最近 2 个完整轮次 + 中期摘要 | 约 800 |
| RAG 查询理解 | 已消解后的完整 query | 轻量视图 |
| 证据自检 | 标准 query + 本轮 RAG 证据 | 独立约束，不读摘要/长期记忆 |
| 主 Agent | system + 短期窗口 + 摘要/长期记忆 + 本轮证据 + 工具 Schema | 总输入约 8000 |
| 摘要器 | 旧摘要 + 本次滑出段 | 仅处理中期记忆 |
| 长期记忆抽取器 | 游标后的新增对话 + 少量已有相关记忆 | 最多抽取 4 条候选 |

这种隔离的关键是：历史偏好可以帮助补全“上次那个”，但不能成为“能否退款”的证据，
也不能影响证据自检放行。自检仍处在生成前，只对临界 Reranker 分数区间的本轮检索证据做充分性判断，异常时 fail closed。
